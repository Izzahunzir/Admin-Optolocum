# Next Flutter integration contract

These endpoints describe existing emulator-only handlers, not active production routes. The real preparation server intentionally does not mount them. Activation requires a separately reviewed server implementation, TLS/connectivity policy, abuse controls and compatible rules.

Configure the backend base URL by explicit environment/build selection; never put Admin SDK credentials in Flutter. The preparation server now serves HTTPS only, with explicitly configured Host, loopback Chrome origin and optional native-client policies. USB with `adb reverse` uses `https://localhost:8787`; trusted LAN uses the configured private IP and matching certificate SAN. The Flutter client must trust only the intended development CA and retain hostname validation. See [SECURE_LOCAL_CONNECTIVITY.md](SECURE_LOCAL_CONNECTIVITY.md) for exact setup. Plain LAN HTTP must never carry passwords, tokens or documents.

New signup: `POST /api/enrollment`, JSON `{requestId, recoverySecret, email, password, accountType, profile}`. Generate 16 random bytes as 32 lowercase hex for `requestId` and 32 random bytes as 64 lowercase hex for `recoverySecret`. Normalize email lowercase/trimmed. `accountType` is `locum` or `practice_owner`; locum profile is exactly `{fullName}`, owner profile is exactly `{fullName, phoneNumber, role}` with role `HR`, `Manager` or `Optical Owner`. Do not send UID, token, claims or verification status. Success is `{data:{uid,accountType}}`. Keep request ID and secret in protected storage until success; retry uncertain responses with the same request parameters and original password. Do not persist passwords or log secrets. After success, sign in using Firebase Auth, clear recovery material, and allow for a fresh login after the access cutoff. Existing Auth accounts need operator recovery, not enrollment by matching email.

Applicant requests require `Authorization: Bearer <Firebase ID token>` verified with revocation checking, a currently enabled non-admin account, matching trusted assignment and active access with `auth_time > validAfter`. `POST /api/applicant/draft` takes JSON `{requestId, accountType, submittedFields}`, where request ID is 32 lowercase hex characters. The locum fields are exactly `fullName`, `email`, `nric`, `phoneNumber`, `gender`, `dateOfBirth`, `highestEducation`, `course`; owner fields are exactly `practiceType`, `clinicName`, `registrationNumber`, `address`, `state`, `contactNumber`, `companyEmail`. Values are strings. Response supplies `submissionId` and state. Reusing a request ID with different fields fails.

Upload with `POST /api/applicant/upload/{requestId}` and raw bytes, `Content-Type: application/pdf`, `image/png` or `image/jpeg`, maximum 50 MiB. Retry with identical bytes only; the server computes metadata and never returns a public URL. Finalize with `POST /api/applicant/finalize`, JSON `{requestId}`; retry with the same ID after an uncertain response. The server validates the private file and finalizes the draft; it does not grant approval. Errors are JSON `{error:{code,message}}`: handle 400 validation, 401 reauthentication, 403 access, 404 missing draft, 409 conflict/recovery, 413 size and 503 temporary unavailability without displaying sensitive data. Do not log submitted fields, credentials, document contents or tokens.

In the main app, replace the isolated logic in `lib/services/demo_enrollment.dart` and direct Firebase signup/profile creation in the Locum and Practice Owner forms with the real transport when enabled. Integrate the existing verification forms with draft/upload/finalize and preserve stable request IDs across retry. Prevent duplicate submissions and distinguish offline/uncertain completion from success. Existing forms and app data must remain intact. Candidate rules require trusted profile approval status `approved` for job posting/application, which must be set only through reviewed verification handling. Test these paths against current rules and existing accounts before cutover.

## Session validation (preparation server)

`POST /api/session/validate` over HTTPS, with `Authorization: Bearer <Firebase ID token>` and `Content-Type: application/json`. The exact JSON body is `{ "accountType": "locum" }` or `{ "accountType": "practice_owner" }`. Do not send a UID. Success: HTTP 200 `{ "data": { "uid": "<verified UID>", "accountType": "locum", "access": "active" } }` (with the requested matching type). Verify all three values against the current Firebase user before navigation. Responses include `Cache-Control: no-store`. HTTP 400 means invalid request, 401 invalid, expired or revoked token, 403 unavailable or mismatched account access, and 503 validation unavailable. Fail closed and sign out on failure. No access record is returned. Each protected operation must independently check authorization.

Production enrollment, applicant mutations and administrator review remain disabled or unmounted. The admin dashboard currently uses a hard-coded local HTTP endpoint and must be adapted to the approved HTTPS transport before real use. Final activation also requires review and automated testing of the transactional submission controls, current deployed rules and candidate rules, document persistence, abuse controls, hosting and the full route wiring. No production mutation activation is authorized by this document.
