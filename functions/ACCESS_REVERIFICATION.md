# Account access and reverification notes

The candidate Firestore rules require `account_access/{uid}` with `state` (`active` or `disabled`) and an integer `validAfter` in Unix seconds. Access requires an ID token whose `auth_time` is strictly greater. Enrollment and administrator assignment create active access with a fresh cutoff. A sign-in in the same second as that cutoff is not sufficient; sign in again after the cutoff. Assignment retry will not overwrite an existing access record. An administrator may recreate a missing record only for an active, already assigned account after reviewing it.

Disable and Enable first write `state: disabled` with an operation marker. They then update Auth, revoke refresh tokens, and only for a confirmed successful Enable activate the access record with a new cutoff. A failed transition is left blocked when the block was committed. Retry the same operation with the original expected state to resume its marker; conflicting transitions require administrator review. Auth and Firestore cannot be atomic, and external Auth changes or an unknown transaction outcome require inspection; do not infer access from Auth alone. Production mutation remains gated. Existing inconsistent records need manual investigation, not bulk repair.

Submitted fields remain in immutable verification revisions while profile status is pending. Approval promotes the reviewed revision's fields in the same transaction as the review and profile status; rejection changes the status without promoting proposed fields. Latest-submission and review transaction checks prevent old revisions winning a race. Existing jobs, applications and review history are not changed.

`approved` is the successful status used for authorization. Existing `verified` values are not automatically equivalent for job or application permissions. Inventory legacy accounts read-only and review reliable contemporaneous approval evidence. An administrator may use a separately audited, compare-and-set recovery procedure to establish approval only after evidence and identity are verified; absent sufficient evidence require new verification. This repository does not implement or execute migration.

The confirmed classification treats the Practice Owner personal full name and role as ordinary editable fields; practice verification does not include the name. Locum email, phone and gender are ordinary fields too. Revisions retain their submitted values for review history, but approval promotes only the classified sensitive fields, preserving newer ordinary edits. Practice verification contact fields remain in the revision and are not mapped onto the owner's editable contact fields. Do not publish the candidate until those rules and all deployed authorization paths have been reviewed and tested.

The latest main-repository candidate checks `activeSession()` on job and application updates as well as creates. The isolated Admin integration test now confirms that disabled and stale sessions cannot update them. The candidate is not deployed; effective production rules and all other authorization paths still require review.
